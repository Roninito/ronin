1. The mental model

Ronin is a daemon. Everything else is a remote control.

You start Ronin once with ronin start and it keeps running — scheduling work, watching files, listening on Telegram and Discord, serving dashboards. The CLI, the chat channels, and the browser are all just different ways of reaching that one running process. This explains the most common first-run surprise: ronin ask fails if Ronin isn't running, because ask is a client, not a standalone command.

Internally, every unit of work in Ronin is a Duty running the SAR loop: Sense (pull in signal — a schedule firing, a file changing, a chat message), Analyze (reason over it with an AI model), Respond (execute tools, emit events, write memory). There is no second execution model. Coordination and scheduling are just Duties whose job is coordinating other Duties.

2. Three concepts: Duty, Tool, Skill

Ronin has exactly three capability concepts. Older names still appear in some files and commands; the translations are below.

ConceptWhat it isLegacy names you may still see
DutyA running SAR loop with a persona, an allowlist of capabilities, and memory. The thing that decides. Lives in duties/.Agent
ToolAn atomic, typed, in-process capability the AI can call directly (function calling). Bundled into Tool Packs.Plugin method
SkillA markdown-defined, language-agnostic capability — can shell out to Python or anything else. Discoverable, installable, shareable. Lives in skills/.Technique, Kata

If you see "agent" in a command or doc, read it as Duty. If you see "kata" or "technique," those concepts have been folded into Skills.

3. Getting started

# One-time setup — the wizard walks you through privacy mode,
# desktop integration, and optional cloud AI keys
ronin init

# Or accept the recommended defaults
ronin init --quick

# Start the daemon (leave this running)
ronin start

The wizard's defaults are the most private configuration: local AI only (Ollama), nothing leaves your machine, works offline. Cloud providers are opt-in and can be added later.

Once it's running, verify from another terminal:

ronin status          # is it up, what's scheduled
ronin list            # all loaded duties
ronin list-routes     # every URL the running instance serves

Because duties add routes dynamically, the authoritative list is always ronin list-routes. Make that your discovery habit — new duties often ship new pages.

6. Writing a Duty

A Duty is a TypeScript class in duties/ (project) or ~/.ronin/agents (shared across projects). It declares how it wakes up — a cron schedule, a file watch, a webhook, or any combination — and gets an api object for everything else.

import { BaseDuty } from "../src/duty/index.js";
import type { DutyAPI } from "../src/types/index.js";

export default class DigestDuty extends BaseDuty {
  static schedule = "0 9 * * 1-5";      // weekdays at 9am
  static watch = ["notes/**/*.md"];      // optional
  static webhook = "/webhook/digest";    // optional

  constructor(api: DutyAPI) { super(api); }

  async execute(): Promise<void> {
    const recent = await this.api.memory.getRecent(10);
    const summary = await this.api.ai.complete(
      `Summarize these notes: ${JSON.stringify(recent)}`
    );
    await this.api.memory.store("daily-digest", summary);
  }
}

You don't have to write duties by hand. ronin create agent "monitor log files and alert on errors" generates one interactively with AI assistance, and ronin run <name> executes any duty once, on demand, for testing.

7. The API object

Every Duty receives this.api. The namespaces you'll use constantly:

NamespaceWhat it gives you
api.aicomplete, chat, stream, and callTools (function-calling loop). Routed through model tiers.
api.memoryStore/retrieve/search persistent memory (SQLite-backed)
api.filesRead, write, list, watch files
api.dbDirect SQL: query, execute, transaction
api.eventsThe event bus: emit, on. How duties talk to each other.
api.httpOutbound requests, plus registerRoute to serve pages
Direct plugin APIsapi.git, api.shell, api.telegram, api.discord, api.scrape, api.rag, api.email, and more

The one rule of the architecture worth internalizing: duties communicate through events, not by calling into each other. One scheduler, one bus, and a single state-owning duty per domain (for example, the Todo duty owns the kanban).

8. Skills

Skills are markdown-defined capabilities that live in skills/ and ~/.ronin/skills. Unlike Tools, they're language-agnostic — a skill can run Python, shell scripts, or anything else. They follow the open AgentSkills standard, which means you can install skills from the public ecosystem.

ronin skills list                        # what's installed
ronin skills discover "log monitor"      # search skills.sh + playbooks.com
ronin skills explore <name>              # read a skill's full docs
ronin skills use <name> --ability=x --params='{...}'
ronin create skill "monitor logs and alert on errors"

A skill is just a folder with a SKILL.md — frontmatter (name, description) plus documentation of its operations. Ronin reads these to know when and how to use each skill during conversations and duty runs.

9. Artifacts

Artifacts are Ronin's persistent project containers — the feature to reach for whenever work spans more than one session. An Artifact tracks a multi-step collection or research project across every chat, Discord message, and duty that touches it, and it knows when it's done.

What an Artifact does

Each Artifact has a lifecycle (INITIALIZED → ACTIVE → PROCESSING → REVIEW → COMPLETE → ARCHIVED), asset categories with target/collected/pending counts, a completion threshold (85% by default), an activity log, and its own dashboard at /artifact/<id>. Files gathered for the project are stored under the artifact and served from its dashboard.

Using them in conversation

You mostly don't manage Artifacts manually — you mention them. Say "let's gather 3D models and textures for the game" and Ronin will propose creating an Artifact. Later, in a completely different chat, say "add some vehicle models to the game assets" and Ronin recognizes which project you mean (by id, name, or tag relevance), pulls its current state into context, and records the new work. This auto-detection runs on Telegram and Discord today; elsewhere, Ronin still knows the artifact_* tools exist but won't proactively surface a specific project's state unless you name it.

Why it doesn't loop forever

The artifact-manager duty sweeps active artifacts every 15 minutes and asks a gated question: is this project due for more work? The gate enforces exponential backoff between check-ins (1h, 1.5h, 2.25h…), a maximum attempt count, relevance scoring on new context, and a hard stop once the project is COMPLETE or ARCHIVED. When an artifact does come due, Ronin nudges you on Telegram or Discord with what's pending and a dashboard link, rather than silently burning cycles. Completed projects can be re-opened by asking.

The tools

Eight artifact_* tools are available to the AI in any conversation: create, load, updateProgress, addAsset, appendLog, schedule, transitionState, and getSchedulingStatus. You can invoke them indirectly ("mark the game assets project complete") — you never need to call them yourself.

10. The Plan Workflow

The Plan Workflow turns a chat message into approved, executed work, with a human gate in the middle.

1. Propose   →  Telegram message: "#ronin #plan Create user auth system"
2. Track     →  The Todo duty adds it to the kanban at /todo
3. Approve   →  You approve on the board (or POST /api/plans/approve)
4. Execute   →  The Coder Bot picks up the approved plan and runs it
5. Observe   →  Every transition emits events; observers alert and log

The design guarantees are worth knowing: all communication is events, the Todo duty is the only owner of plan state, and the Coder Bot is a pure reactor that only acts on approved plans. Nothing executes without your approval.

11. Coding Tasks (multi-executor)

The same kanban board that runs the Plan Workflow can hand a card to a real coding agent — Claude, opencode, qwen, cursor, or Gemini — working inside its own isolated git worktree, with your review in the loop before anything merges into your repo.

Picking an executor

Tag a card #claude, #opencode, #qwen, #cursor, or #gemini to pick that executor explicitly. An untagged command that clearly implies file or code work falls back to your configured default (claude out of the box); anything else stays on Ronin's own tool-calling loop, unchanged — coding execution is opt-in per command, never the default path.

Worktrees, review, and merge

Every coding-executor command gets its own git worktree on a fresh task/<card-id> branch, so parallel cards never share a writable ref. When the executor finishes, a card with file changes moves to a new Review column with the diff attached; no changes means it goes straight to Done, same as any other command. Approve on the Review card (or POST /api/todo/commands/approve) to dry-run the merge, fast-forward your base branch, and release the worktree. If it conflicts — something else merged while this sat in Review — Ronin spins up a linked conflict-resolution card in the same worktree automatically, rather than leaving you to sort it out by hand. Cards in Review are also rechecked periodically, so a conflict can surface before you ever click Approve.

Leaving feedback

A comment on a Review card (POST /api/todo/commands/resume) sends it back for another round — the executor resumes its actual session in the same worktree rather than starting over, and the diff can be viewed per round or cumulatively.

From one goal to many cards

Give the board a goal instead of a pre-chopped task list — "ship the CSV export feature" — and Ronin breaks it into linked cards with dependencies, tagging each with the executor it thinks fits. Cards labeled #auto start themselves the moment their prerequisites land in Done.

Safety

Coding executors run shell commands and write files, so any command that resolves to one from an untrusted source (a Discord or Telegram message, for instance) is held for your explicit approval before it ever touches a worktree — the same pending-response mechanism used elsewhere in Ronin, not a separate system. Commands you create yourself, from the board or a channel you've explicitly marked trusted, run immediately.

12. Models and privacy

Ronin's default posture is fully local: Ollama on localhost:11434, no data leaving the machine, functional without internet. Cloud AI is a tiered opt-in, not a requirement.

TierMeaning
localOllama models on your machine (the default)
smartYour configured "better" model — local or cloud, your choice
cloudRemote providers (Anthropic, OpenAI, Grok, Gemini) — requires API keys

Manage local model definitions with ronin ai add / list / run, and set cloud keys with ronin config --grok-api-key … etc. When cloud tools are used, Ronin surfaces estimated costs and asks before expensive operations.

14. Troubleshooting

SymptomCause and fix
ronin ask can't connectThe daemon isn't running. ronin start first — ask is a client.
Commands produce no outputYou're not in the ronin directory. cd into it (or install globally with bun link).
A dashboard 404sThe owning duty isn't loaded, or the instance restarted. Check ronin list and ronin list-routes.
AI responses fail locallyOllama isn't running or the model isn't pulled: ollama run qwen3:1.7b once to fetch it.
Cloud tier errorsMissing API key. ronin config --show to verify, remembering env vars win over config.json.
Duty didn't fire on scheduleCheck the cron expression (minute hour day month weekday) and confirm the duty appears in ronin status.
Artifact stopped getting attentionBy design: it hit COMPLETE, max attempts, or backoff. Its dashboard shows which. Mention it in chat to re-engage.
Coding task card stuck in To DoIt's held for approval — a coding executor was requested from a channel that isn't in tasking.trustedChannels. Approve the pending-response card to release it.
Coding task card fails immediately with no worktreeIts board has no default_repo set (or the card has no repo_path override). Coding executors fail fast rather than guessing a repo.
